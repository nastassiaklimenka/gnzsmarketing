# Workflow: batched SEO production

## Назначение

Этот workflow используется, когда нужно вести SEO-производство поэтапно, начиная с одной статьи, а затем масштабировать процесс в батчи.

Единица производства:

- 1 кластер = 1 статья.

Базовый стартовый цикл:

- 1 цикл = 1 кластер = 1 исследование = 1 статья.

Масштабирование:

- после отладки процесса один цикл можно расширять до батчей.

## Обязательные правила

- Не переходить к исследованию, пока кластер явно не утвержден пользователем.
- Не переходить к написанию статьи, пока исследование явно не утверждено пользователем.
- Не переходить к верстке или подготовке к публикации, пока текст явно не утвержден пользователем.
- Не использовать молчаливое согласование.
- Если цикл отклонен на любом этапе, не переходить дальше, пока пользователь явно не утвердит исправленную версию.

## Входные данные

Перед запуском цикла получить или определить:

- тему или тематическое направление;
- регион продвижения, если он важен;
- целевой тип контента: статьи в блог;
- критерий отбора: среднечастотные кластеры;
- стартовый размер цикла: 1 статья.

Если какие-то параметры не даны явно, делать разумные предположения и фиксировать их в материалах цикла.

## Порядок работы

### 1. Создать или выбрать рабочий цикл

1. Использовать существующую рабочую папку или создать новую по шаблону `batch-01`, `batch-02`, `batch-03`.
2. Внутри рабочей папки хранить все файлы одной итерации плоско, без дополнительных подпапок по этапам.
3. На стартовом этапе допускается, что в рабочей папке будет только один кластер и одна статья.
4. Не смешивать материалы разных циклов в одной папке.

### 2. Собрать 1 кластер на согласование

1. Собрать семантику и сгруппировать ее по правилам `seo-semantics`.
2. Отобрать 1 среднечастотный кластер, где:
   - один кластер соответствует одной будущей статье;
   - есть понятный информационный или прикладной интент;
   - тему можно раскрыть с пользой и с опорой на экспертизу Генезис.
3. Для кластера зафиксировать:
   - cluster slug;
   - главный запрос;
   - поддерживающие запросы;
   - интент;
   - ориентир по частотности;
   - угол статьи;
   - почему кластер стоит брать;
   - риски.
4. Сохранить материалы в:
   - `cluster_candidates.csv`
   - `cluster_review.md`
5. Передать пользователю только на явное утверждение.

### 3. Остановиться и дождаться явного решения по кластерам

1. Не переходить к следующему этапу без явного ответа пользователя.
2. Если пользователь отклонил кластер:
   - заменить или доработать его;
   - снова отправить на согласование;
   - не переходить к исследованию до явного утверждения.

### 4. Провести исследование по утвержденному кластеру

1. Для утвержденного кластера провести исследование по правилам `seo-semantics`.
2. Обязательно проверить:
   - динамику спроса;
   - признаки растущего, падающего или стабильного спроса;
   - сезонность;
   - формулировки спроса и смещение интента;
   - ТОП по главному запросу и 3-5 поддерживающим.
3. Для конкурентов в выдаче выписать:
   - тип страницы;
   - H1;
   - title;
   - description;
   - ключевые H2/H3;
   - повторяющиеся блоки;
   - CTA;
   - сильные и слабые стороны.
4. На основе анализа сформулировать:
   - что обязательно включить в нашу статью;
   - что раскрыть лучше конкурентов;
   - какие метатеги рекомендовать.
5. Сохранить материалы в `research_<cluster_slug>.md`.

### 5. Остановиться и дождаться явного решения по исследованиям

1. Не писать статьи, пока исследования явно не утверждены пользователем.
2. Если по исследованию есть правки, сначала обновить исследование, затем снова отправить на согласование.

### 6. Написать статью по утвержденному кластеру

1. Для утвержденного кластера и утвержденного исследования использовать `seo-text-write`.
2. В статье обязательно отразить:
   - главный интент;
   - рабочий title;
   - H1;
   - description;
   - отдельный блок `SEO-разметка для публикации` с HTML-метатегами `<title>`, `<meta name="description" content="...">`, canonical при наличии slug и полной картой H1/H2/H3;
   - логичную H2/H3-структуру;
   - короткий ответ или summary;
   - практические блоки;
   - FAQ;
   - мягкий CTA;
   - внутреннюю перелинковку.
3. Не писать обобщенный или пустой SEO-текст.
4. Делать статью полезной даже без знания контекста компании.
5. Сохранить материал в `article_<cluster_slug>.md`.

### 7. Остановиться и дождаться явного решения по текстам

1. Не переходить к Tilda-подготовке, пока текст явно не утвержден пользователем.
2. Если по статье есть правки, доработать ее и снова отправить на согласование.

### 8. Подготовить карты верстки под Tilda

1. Для утвержденной статьи подготовить карту стандартных блоков Tilda.
2. Зафиксировать:
   - первый экран;
   - оглавление;
   - основные контентные блоки;
   - таблицы и чек-листы;
   - FAQ;
   - внутренние переходы;
   - финальный CTA;
   - места для кейсов, виджетов, формы и блока `Читайте также`.
3. Сохранить материалы в `tilda_map_<cluster_slug>.md`.

### 9. Публикация через MCP

1. Выполнять этот шаг только если доступен рабочий Tilda MCP или другой подтвержденный коннектор.
2. Если коннектора нет:
   - не обещать автоматическую публикацию;
   - подготовить `tilda_map` как handoff для ручной верстки или будущей автоматизации.

## Формат результата по циклу

Итогом одного рабочего цикла должны быть:

- 1 кластер на согласование;
- 1 утвержденное исследование;
- 1 утвержденная статья;
- 1 карта верстки под Tilda;
- явная фиксация, какие материалы утверждены, а какие возвращены на доработку.

## Критерии готовности

Цикл готов, если:

- для утвержденного кластера есть исследование;
- для утвержденного исследования есть статья;
- для утвержденной статьи есть `tilda_map`;
- ни один переход между этапами не был выполнен без явного подтверждения пользователя.
